   1. Resumen ejecutivo   

  El proyecto consiste en construir una experiencia web educativa autogestionada, desplegada inicialmente como prueba de concepto en GitHub Pages. El sitio transformará el diseño curricular de 19 semanas en una interfaz navegable, responsiva y accesible, con contenidos estructurados por módulos, semanas y capas pedagógicas. No se desarrollará un backend completo, sistema de matrícula, autenticación institucional ni almacenamiento central de entregables en esta etapa.                         

       Conclusión preliminar de complejidad   



    La complejidad funcional es media-alta por el volumen y la diversidad de contenidos, pero la complejidad de infraestructura puede mantenerse baja mediante una arquitectura estática basada en HTML, CSS y JavaScript, con contenido desacoplado en Markdown o JSON. El principal reto no es el backend: es diseñar una arquitectura de contenidos sostenible, navegación clara, persistencia local, componentes reutilizables y una disciplina de documentación que permita trabajo coordinado entre personas y modelos de IA.      



   

  El diseño curricular define seis bloques: Fundamentos y los módulos A-E. Cada semana sigue una secuencia recurrente: logro, introducción, teoría, video, tarea con prompt CIFRCE, actividad complementaria y Chispa de Innovación. Esta repetición es favorable para un sistema de componentes y plantillas. Sin embargo, el documento incluye aproximadamente 48 páginas, 19 semanas, múltiples tipos de actividades, referencias, avisos de privacidad y vínculos con GPTs especializados, por lo que no conviene codificar cada página manualmente.   





   2. Base documental y lectura preliminar   

  La valoración se basa en el archivo “diseno_curricular_toolkit_v23.docx”, que establece la estructura del programa, los contenidos semanales, las actividades, los entregables, la lógica de GPTs personalizados y las fuentes conceptuales. El documento prevé cerca de 76 horas de estudio distribuidas en 19 semanas y una carga estimada de 3 a 4 horas por semana.

   3.2 Fuera de alcance en esta etapa   





   Autenticación de personas usuarias, perfiles y recuperación de contraseña.   





   Matrícula, gestión de cohortes o roles de mediación.   





   Base de datos centralizada y sincronización entre dispositivos.   





   Recepción, almacenamiento o evaluación de entregables.   





   Foros internos, mensajería o notificaciones.   





   Analítica individual vinculada a identidad personal.   





   Integración directa con API de OpenAI, WhatsApp, correo o sistemas UCR.   





   Panel administrativo o CMS con edición desde navegador.   





   Procesamiento de pagos, certificados verificables o transacciones sensibles.                         

       Regla de alcance   



    Toda funcionalidad que requiera identidad, almacenamiento central, permisos, secretos de API o procesamiento de datos personales debe tratarse como una fase posterior con backend y revisión institucional.

   6.3 Recomendación de formato   

  Usar Markdown para textos largos y JSON para metadatos, navegación y estructuras repetibles. Esta combinación facilita lectura humana, control de versiones y procesamiento automático. Una alternativa es mantener cada semana en un archivo Markdown con front matter; deberá decidirse en la fase de prototipo técnico.   





   7. Arquitectura técnica recomendada   

  Para la prueba de concepto se recomienda una aplicación web estática progresiva, sin framework pesado en la primera iteración. GitHub Pages publica archivos HTML, CSS y JavaScript desde un repositorio y permite incorporar un proceso de construcción con GitHub Actions. Esta plataforma es adecuada para una experiencia educativa sin datos sensibles ni transacciones.

       Decisión arquitectónica sugerida   



    Comenzar con una “multi-page application generada” o una SPA ligera con hash routing. No adoptar React/Vue en la primera fase salvo que la auditoría del sitio previo demuestre una ventaja concreta. El objetivo es reducir dependencias y facilitar mantenimiento por equipos mixtos y agentes de IA.

   10. Gobernanza del trabajo con modelos de IA   

  La continuidad entre Antigravity, Claude y personas desarrolladoras depende de que el estado real del proyecto viva en el repositorio, no en la memoria de una conversación. Cada sesión debe comenzar leyendo archivos de orientación y terminar actualizándolos.                                



         Archivo                



         Propósito                



         Regla de actualización                 



       README.md               



       Instalación, ejecución, arquitectura resumida y despliegue.               



       Cuando cambie el modo de operar el proyecto.                 



       PROJECT_STATUS.md               



       Estado actual, tarea en curso, bloqueos y siguiente paso.               



       Al inicio y cierre de cada sesión relevante.                 



       CHANGELOG.md               



       Cambios visibles por versión.               



       Con cada conjunto de cambios aceptado.                 



       AGENTS.md               



       Reglas para modelos: lectura obligatoria, comandos, convenciones y límites.               



       Cuando cambien procesos o herramientas.                 



       docs/decisions/               



       Registros ADR de decisiones técnicas.               



       Ante decisiones no triviales o difíciles de revertir.                 



       CONTRIBUTING.md               



       Flujo de ramas, commits, revisiones y criterios de aceptación.               



       Cuando cambie la gobernanza.      



   





   10.1 Protocolo obligatorio por sesión   





   Leer AGENTS.md, PROJECT_STATUS.md, CHANGELOG.md y el ADR más reciente.   





   Inspeccionar git status y los últimos commits antes de modificar archivos.   





   Declarar el alcance de la sesión y no mezclar tareas no relacionadas.   





   Ejecutar validaciones y pruebas antes de cerrar.   





   Actualizar PROJECT_STATUS.md con lo realizado, pendientes, riesgos y siguiente paso.   





   Agregar una entrada a CHANGELOG.md cuando exista una mejora funcional o visual validada.   





   Usar commits pequeños con mensajes descriptivos y no sobrescribir trabajo ajeno.

   14. Criterios de aceptación del PoC   





   Las 19 semanas se pueden navegar desde un mapa curricular coherente.   





   Cada semana presenta sus capas en el orden definido por el diseño curricular.   





   Los prompts conservan Contexto, Instrucción, Formato, Restricciones y Criterios de éxito cuando corresponda.   





   Una persona puede marcar avance y recuperarlo al volver desde el mismo navegador.   





   El sitio funciona en anchos móviles y de escritorio sin desbordamientos horizontales.   





   Todas las funciones esenciales son utilizables con teclado.   





   Los textos, botones y estados cumplen contraste y foco visible.   





   Una semana nueva puede agregarse modificando contenido, sin duplicar una página HTML completa.   





   Cada cambio significativo queda registrado en CHANGELOG.md y PROJECT_STATUS.md.   





   El despliegue se ejecuta automáticamente tras integrar cambios aprobados en la rama principal.   





   No se recopilan datos personales ni se envía información a un servidor propio.

   16. Decisiones que deben validarse antes de programar   





   ¿El PoC será una SPA ligera, un sitio multipágina generado o una combinación?   





   ¿El contenido se mantendrá en Markdown con front matter o en JSON más Markdown?   





   ¿Se requiere un diagnóstico inicial que recomiende una ruta o todas las personas siguen el orden completo?   





   ¿El avance se marcará por semana o también por cada capa interna?   





   ¿Los videos se alojarán en YouTube, Vimeo, UCR u otra plataforma?   





   ¿Los GPTs especializados se enlazarán desde el sitio y cuáles estarán disponibles en el piloto?   





   ¿Qué lineamientos de identidad visual institucional deben aplicarse?   





   ¿Se requiere español inclusivo, tratamiento de “usted” y reglas editoriales adicionales?   





   ¿Qué navegadores y dispositivos se consideran mínimos?   





   ¿Se incorporará una exportación local de progreso en el PoC o se pospone?
